# Частина 3. Робота з footer.php

## Призначення

- `footer.php` відповідає за нижню повторювану частину сайту і завершення HTML-документа.
- Якщо користувач просить тільки записати або оновити інструкції, не виконувати саму інтеграцію footer.

## Що має бути в footer.php

- Повторюваний HTML-блок footer з верстки: логотип, меню, контакти, адреси, телефони, графік роботи, кнопки, соціальні мережі, копірайт та інші нижні елементи.
- Нижні приховані блоки, modal-вікна, templates або службові повторювані елементи, якщо у вихідному HTML вони розташовані ближче до footer.
- Закриття основних wrapper-блоків, якщо вони були відкриті в `header.php` або `index.php` і логічно мають завершуватися внизу сторінки.
- Виклик `wp_footer();` перед закриттям `body`.
- Закриття тегів `body` і `html`.

## WordPress-адаптація

- Статичні посилання на assets у `footer.php` замінювати на `get_template_directory_uri()`.
- Посилання на головну сторінку замінювати на `home_url('/')`.
- Посилання на email виводити через `mailto:`, телефони через `tel:`, якщо вони є у верстці.
- HTML-структуру не ламати: теги, відкриті вище, мають бути коректно закриті.
- `wp_footer();` має залишатися внизу сторінки перед `</body>`, щоб WordPress міг вивести скрипти та службову розмітку.
- CSS і JS з footer-частини верстки можна інтегрувати через `inc/enqueue.php`, якщо це потрібно для коректної роботи теми.

## Меню WordPress

- Усі меню, які є у footer-верстці, потрібно виводити через стандартний функціонал меню WordPress.
- Для кожної окремої групи footer-меню створювати окрему menu location, якщо ці групи мають редагуватися окремо.
- Не залишати пункти footer-меню жорстко прописаними в `footer.php`, якщо вони мають редагуватися через WordPress.
- Перед створенням footer-меню потрібно проаналізувати всі посилання у footer-верстці і визначити, що є сторінкою, що є зовнішнім посиланням, а що є якорем на блок.
- Перед створенням сторінки для пункту footer-меню потрібно перевірити, чи така сторінка вже існує в WordPress.
- Якщо потрібна сторінка вже створена, не створювати дубль, а використати наявну сторінку і прикріпити її до пункту меню.
- Під час рішення, створювати сторінку чи ні, первинним є URL з верстки, а не тільки текст пункту меню.
- Якщо у верстці URL пункту є якорем, наприклад `#pricing`, не створювати окрему сторінку для цього пункту навіть тоді, коли текст пункту виглядає як назва сторінки.
- Якщо посилання веде на окрему сторінку, спочатку потрібно створити або використати відповідну сторінку WordPress.
- Після створення сторінок потрібно створити меню в базі даних WordPress і додати пункти меню як посилання на відповідні сторінки, а не як довільні custom URL.
- Якщо пункт меню веде на якір на цій же сторінці, його потрібно залишати як якір або посилання на сторінку з якорем відповідно до структури сайту і не створювати для нього окрему сторінку.
- Якщо пункт веде на зовнішній ресурс, email, телефон, файл або месенджер, використовувати відповідний тип посилання і не створювати під нього сторінку WordPress.
- Порядок роботи має бути таким: аналіз посилань з верстки, створення потрібних сторінок, створення footer-меню, прикріплення сторінок до пунктів меню, окреме додавання якірних і зовнішніх пунктів.

## Багатомовні footer-меню

- Якщо встановлений плагін багатомовності, перед створенням сторінок і footer-меню потрібно перевірити, які мови зареєстровані у плагіні.
- Перед створенням перекладу сторінки потрібно перевірити, чи перекладена сторінка вже існує для відповідної мови.
- Якщо перекладена сторінка вже існує, не створювати дубль, а використати її і за потреби зв'язати з основною сторінкою як переклад.
- Для кожної зареєстрованої мови потрібно створити відповідні сторінки цією мовою.
- Перекладені сторінки потрібно зв'язати між собою як переклади однієї сторінки у multilingual-плагіні.
- Заголовки сторінок і пунктів меню для іншої мови потрібно перекласти відповідною мовою, а не дублювати український текст.
- Відносно кількості зареєстрованих мов потрібно створити окремі дублікати кожного footer-меню для кожної мови.
- Footer-меню кожної мови має містити пункти, прикріплені до сторінок цієї ж мови, а не до сторінок іншої мови.
- Меню різних мов потрібно зв'язати між собою як переклади одного меню, якщо це підтримує multilingual-плагін.
- Якщо використовується Polylang, кожне мовне footer-меню потрібно прикріпити до відповідної мовної локації меню, наприклад `footer menu 1 Українська` і `footer menu 1 Русский`.
- Для Polylang потрібно перевірити, що у його налаштуваннях `nav_menus` для активної теми кожна footer-location має menu ID для кожної мови.

## Налаштування footer в адмінці

- Для інформації footer, яка не є меню, потрібно створити або розширити глобальну сторінку налаштувань через ACF Pro.
- На сторінці налаштувань має бути окремий tab `Footer`.
- До tab `Footer` додавати поля для логотипу footer, контактів, телефонів, адрес, графіка роботи, email, соціальних мереж, кнопок, копірайту, текстових блоків, месенджерів та інших подібних елементів.
- Якщо для логотипу footer створюється ACF-поле, потрібно завантажити відповідний логотип у медіабібліотеку WordPress і записати його в це поле в адмінці.
- Не залишати поле логотипу порожнім, якщо у верстці вже є відповідний файл логотипу.
- Не створювати для клієнта технічні ACF-поля на кшталт `CSS-клас іконки`, класів верстки, службових селекторів або інших технічних параметрів дизайну.
- Якщо у повторюваному списку з верстки кожен елемент має свою іконку через іконковий шрифт, наприклад Font Awesome, потрібно створити зрозуміле ACF-поле `Іконка` типу `Select` з людськими назвами варіантів.
- Значення select для шрифтових іконок має бути внутрішнім ключем, наприклад `telegram`, `viber`, `facebook`, `instagram`, а відповідний CSS-клас іконки потрібно визначати в коді теми.
- Якщо у повторюваному списку іконка у верстці є файлом, SVG або `<img>`, потрібно створити ACF-поле `Іконка` типу `Image` або `File` і виводити її через `<img>`.
- Не змішувати принципи: шрифтові іконки керуються через `Select`, файлові іконки через `Image` або `File`.
- Іконки, CSS-класи та інші технічні деталі відображення залишати в коді теми, якщо вони не є контентною частиною повторюваного елемента.
- Якщо елемент складається з кількох частин, поля потрібно розділити або згрупувати логічно.
- Перед кожною логічною групою ACF-полів потрібно додавати поле типу `Message` як заголовок групи в адмінці.
- Таке `Message`-поле має мати ширину `100%`, щоб візуально розмежувати групу і перенести наступні поля на новий рядок.
- Заголовок `Message` має пояснювати, до якого блоку належать наступні поля, наприклад контакти, графік роботи, попап заявки, форма заявки, кнопки, соціальні мережі або інший логічний блок з верстки.
- Якщо кілька ACF-полів належать до одного логічного блоку у верстці, їх потрібно розташовувати поруч у адмінці через налаштування ширини поля, щоб редактор бачив зв'язок між ними.
- Для парних пов'язаних полів, наприклад зображення і його alt-текст, можна використовувати пропорцію ширини `50%` на `50%`, якщо це зручно для заповнення.
- Для груп з трьох пов'язаних полів можна використовувати приблизно рівні колонки або іншу пропорцію, яка відповідає обсягу контенту.
- Якщо частина полів має короткий зміст, наприклад короткий текст кнопки, короткий заголовок блоку або перемикач, таким полям можна задавати меншу ширину в адмінці, наприклад `15%`, `20%`, `25%` або `33%`, а ширші поля залишати для довшого контенту.
- Ширину ACF-полів потрібно підбирати не жорстко за назвою поля, а за логікою блоку, довжиною очікуваного контенту і зручністю редагування в адмінці.
- Якщо у верстці є список однотипних опцій, наприклад телефони, адреси, email, соціальні мережі, месенджери, реквізити або пункти контактів, можна використовувати тип поля ACF `Repeater`.
- Для блоків на кшталт `Наші телефони`, `Графік роботи`, `Адреса`, `Соціальні мережі` потрібно створювати окреме ACF-поле для заголовка блоку і окреме поле або `Repeater` для самих значень.
- Якщо у footer є кілька колонок з різними групами інформації, кожну групу потрібно структурувати окремо: заголовок групи, список значень, посилання, іконки та додатковий текст.
- Кнопки або CTA-елементи у footer мають мати окремі поля для тексту, посилання або modal target, і за потреби додаткових атрибутів.
- У `footer.php` потрібно виводити ці значення з налаштувань, а не залишати їх жорстко прописаними, якщо вони мають редагуватися в адмінці.

## Багатомовні ACF options

- Якщо сайт багатомовний, потрібно перевірити, чи підтримує поточна версія Polylang мовні значення для ACF options page.
- Якщо встановлений плагін `ACF Options For Polylang`, глобальні ACF options для footer потрібно заповнювати окремо для кожної мови через мовний перемикач в адмінці.
- Для `ACF Options For Polylang` потрібно враховувати, що значення можуть зберігатися з мовним суфіксом locale, наприклад `options_ru_RU_*`, а не тільки в базових `options_*`.
- Контент footer у глобальних ACF options потрібно перекладати для кожної мови: тексти кнопок, заголовки контактів, адреси, графік роботи, копірайт та інші текстові значення.
- Спільні для мов елементи, наприклад той самий логотип або однаковий телефон, теж потрібно заповнити у мовних options, якщо поле не підтягується автоматично як fallback.

## ACF і плагіни

- Перед створенням полів або сторінок налаштувань потрібно перевірити, які плагіни встановлені та активні у Docker-оточенні WordPress.
- Особливо перевіряти, чи доступний ACF Pro.
- Якщо ACF Pro доступний, поля для footer потрібно створювати так, щоб їх можна було редагувати в адмінці WordPress.
- Поля ACF мають бути керовані з адмінки, а не тільки описані через код без можливості редагування користувачем.
- Групи полів ACF мають бути видимі в ACF -> Групи полів, якщо користувач має надалі редагувати структуру полів через адмінку.
- Якщо потрібно створити ACF option page або field groups, робити це з урахуванням того, щоб користувач міг редагувати значення через адмінку.
- Не ховати важливі значення footer тільки в PHP-коді, якщо вони мають бути контентом або налаштуваннями сайту.

## Перевірка

- Після змін у `footer.php` потрібно перевіряти себе не тільки синтаксично, а й візуально у браузері.
- Візуально перевіряти desktop і mobile стани footer, меню, колонки, контакти, логотип, соціальні мережі, кнопки, копірайт, приховані нижні блоки, modal-вікна та відступи.
- Якщо сайт багатомовний, перевірити footer для кожної мови окремо.
- Якщо проєкт працює через Docker, відкривати локальний сайт у браузері через Docker URL проєкту і перевіряти, що footer виглядає як у верстці.
