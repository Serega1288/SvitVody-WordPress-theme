# Частина 4. Конструктор секцій через ACF Flexible Content

## Призначення

- Реалізувати власний конструктор сторінок на основі ACF Pro Flexible Content.
- Вихідна точка цього етапу - секції змінного контенту, зібрані в `index.php` після виконання частини 1.
- Кожна секція має отримати окремий PHP-шаблон, відповідний layout гнучкого вмісту та поля для редагування її контенту.
- Якщо користувач просить тільки сформувати або доповнити інструкцію, виконувати лише зміни документації.
- Загальні правила середовища, роботи зі старими файлами та assets застосовувати з частини 1.

## Початковий аналіз і погодження джерел даних

- Перед реалізацією прочитати поточні файли теми, проаналізувати секції `index.php` та відповідну HTML-верстку, включно з мобільними варіантами й інтерактивними станами.
- Перевірити встановлені й активні плагіни у Docker, версію та можливості ACF Pro, зареєстровані типи записів, таксономії, групи полів і мови Polylang.
- На початку виконання узгодити, чи потрібні власні типи записів і які блоки мають використовувати їхні дані. Якщо рішення вже надане користувачем, застосувати його без повторного погодження.
- Подати короткий перелік секцій із запропонованими джерелами даних: власні поля секції, Repeater або зв'язок із типом запису/таксономією. Дати користувачу можливість вказати відповідність між блоками й сутностями.
- Для невизначених блоків із товарами, категоріями, пропозиціями або цінами запитати, чи це самостійний контент, чи вибірка із записів. Не робити висновок тільки за зовнішнім виглядом карток або назвою секції.
- Поки зв'язок не погоджено, можна виконувати незалежні частини; модель даних спірного блоку має дочекатися відповіді.
- Звичайні інформаційні списки, кроки, переваги й подібні елементи реалізувати через Repeater. Окремий тип запису потрібен лише для погодженої самостійної сутності.
- Зафіксувати погоджені зв'язки окремо від загальних правил, щоб приклади поточного сайту не стали обов'язковою моделлю для всіх майбутніх блоків.

## Шаблон сторінки Constructor

- Створити в корені теми `page-constructor.php` із заголовком `Template Name: Constructor`.
- Використати стандартні `get_header()`, WordPress Loop, `get_template_part('inc/box', 'constructor')` і `get_footer()`.
- Зберегти потрібні для поточної теми обгортки, класи й атрибути. Приклад нижче показує структуру викликів; перед застосуванням звірити відкриття та закриття обгорток із поточною темою, щоб не дублювати `main` та його ID.

```php
<?php
/**
 * Template Name: Constructor
 *
 * @package ProjectTheme
 */

get_header();
?>
<main id="swup" class="transition-fade" role="main">
    <div class="template-page constructor">
        <?php while (have_posts()) : the_post(); ?>
            <?php get_template_part('inc/box', 'constructor'); ?>
        <?php endwhile; ?>
    </div>
</main>
<?php get_footer(); ?>
```

- Створити групу полів ACF із правилом показу `Page Template == page-constructor.php`.
- Для сторінок цього шаблону приховати стандартний редактор контенту, зберігши заголовок сторінки, вибір шаблону й мовні налаштування. Перевірити це в активному редакторі WordPress; інші шаблони не зачіпати.
- У цій групі створити поле типу `Flexible Content` з ім'ям `constructor`.
- Структура групи та її layouts має бути видимою й редагованою в `ACF -> Групи полів`, а значення - на сторінках із шаблоном `Constructor`.
- Не перезаписувати зміни структури або значень, зроблені редактором в адмінці, автоматично при кожному завантаженні сайту.

## Диспетчер секцій

- Створити `inc/box-constructor.php`, який перебирає `have_rows('constructor')`, викликає `the_row()` і визначає шаблон через `get_row_layout()`.
- Використати явну відповідність layout до `get_template_part()` за наданим принципом. Не будувати довільний шлях PHP-файлу з редагованого поля.
- У кожному layout створити поле `disable_block` типу `True / False`, початково вимкнене. Увімкнене значення приховує секцію на сайті, зберігаючи її дані в адмінці.
- Підтримати необов'язковий `constructor_name` в `$args`, лічильник секцій та суфікс для ідентифікаторів повторюваних елементів. Для сумісності з наданим прикладом допустимий і скалярний аргумент.
- Дотримуватися одного формату передавання `$section_suffix` у шаблони секцій. У наведеному підході третій аргумент `get_template_part()` є рядком, доступним у шаблоні як `$args`.

```php
<?php
$constructor_name = '';
if (is_array($args)) {
    $constructor_name = isset($args['constructor_name'])
        ? (string) $args['constructor_name']
        : '';
} elseif (is_scalar($args) || null === $args) {
    $constructor_name = (string) $args;
}

$step_section = 0;
while (have_rows('constructor')) :
    the_row();
    $section_index = $step_section++;
    $section_suffix = '' !== $constructor_name
        ? $section_index . '-' . $constructor_name
        : (string) $section_index;

    if (get_sub_field('disable_block')) {
        continue;
    }

    if ('template-banner-promo' === get_row_layout()) {
        get_template_part('inc/template/banner', 'promo', $section_suffix);
    }
endwhile;
```

- `template-banner-promo` тут є прикладом іменування. Додати явні гілки для всіх фактично створених layouts.
- Порядок секцій на сайті визначає порядок рядків Flexible Content. Редактор повинен мати можливість додавати, переставляти, повторювати та вимикати секції.
- У порожнього конструктора не має бути PHP-помилок або автоматичного повернення всіх статичних блоків.

## Шаблони секцій та іменування

- Створити папку `inc/template` і перенести туди розмітку секцій з `index.php`, кожну в окремий шаблон.
- Для layout використовувати ім'я `template-<назва-блоку>`, для PHP-файлу - ту саму назву без префікса `template-`.
- Приклад відповідності: layout `template-banner-promo` -> файл `inc/template/banner-promo.php` -> виклик `get_template_part('inc/template/banner', 'promo', $section_suffix)`.
- Назви формувати за змістом фактичної секції; підписи layouts в адмінці робити зрозумілими українською.
- Однакові за структурою секції реалізувати одним повторно використовуваним layout; наповнення зберігати в окремих рядках або сторінках.
- Усередині шаблону використовувати `get_sub_field()` та вкладені повторювачі поточного layout.
- Зберегти класи, структуру, адаптивність та потрібні JS-атрибути вихідної секції. Замінити статичний контент на поля ACF.
- Для повторних екземплярів секції уникати дублювання DOM ID, ідентифікаторів слайдерів та інших інтерактивних елементів, використовуючи суфікс.
- Зберегти роботу існуючих посилань-якорів. Відомий якір секції має залишатися доступним; повторні екземпляри повинні отримувати інші ID. Не змінювати якір тільки через переставлення рядка конструктора.
- Після перенесення налаштувати `index.php` як коректний fallback теми відповідно до її поточного використання, щоб він не додавав статичні копії секцій поверх конструктора.

## Вибір типів полів ACF

- Усі контентні тексти й медіа секцій мають редагуватися у відповідному layout в адмінці. Враховувати підписи, примітки, одиниці виміру, тексти кнопок, alt-тексти та окремі мобільні варіанти, якщо вони присутні.
- Короткий заголовок або простий однорядковий текст - `Text`.
- Довгий заголовок або великий текст із переносами рядків без абзацної HTML-структури - `Text Area`. Налаштування нових рядків обирати за розміткою: `br` для видимих переносів або без автоматичного форматування, якщо форматування забезпечує шаблон. Не додавати автоматичні `p` там, де їх не передбачає структура.
- Текстовий контент з абзацами `p`, форматуванням і змістовими посиланнями - `Wysiwyg Editor`. Панель редактора та можливість вставки медіа обмежити потребами блоку. Не обгортати результат редактора додатковим `p`.
- Кнопка з власним текстом і URL - `Link` із поверненням масиву; виводити назву, URL і target із поля.
- Вибір внутрішньої сторінки як цільового посилання - `Page Link`, обмежений потрібними типами записів. Якщо потрібен незалежний підпис, створити окреме текстове поле. Для кнопки з власним підписом зберігати принцип `Link`.
- Якір, зовнішній URL, телефон, email та команда відкриття попапу мають зберігати своє призначення. Кнопка відкриття модального вікна не стає посиланням на вигадану сторінку.
- Зображення та фонове фото секції - `Image`. Повернення ID або масиву обрати послідовно й врахувати в шаблоні. Передбачити редагування фону, якщо він є у верстці.
- Файлова іконка, зокрема SVG або зображення з `img`, - `Image` або `File` за підтримкою медіатипу в проєкті, з можливістю вибрати інший файл у медіабібліотеці.
- Іконка зі шрифту - `Select` зі зрозумілими назвами; внутрішні значення зіставити з дозволеними класами в коді. Не створювати текстове поле для введення CSS-класу.
- Список однотипного контенту - `Repeater` з полями відповідного змісту: зображення/іконка, заголовок, опис, посилання, ціна або інші фактично потрібні дані. Не додавати посилання елементу, в якого його немає за змістом.
- Числові значення для розрахунків або сортування - `Number`; форматовані текстові умови ціни зберігати окремо.
- Погоджений вибір записів - `Relationship` або `Post Object`; вибір категорій - `Taxonomy`. Не копіювати дані пов'язаного запису в незалежні поля секції без потреби.
- Вивід екранувати відповідно до контексту: `esc_html()`, `esc_attr()`, `esc_url()`, `wp_kses_post()` для дозволеного форматованого тексту. Не дозволяти довільний HTML для заміни структури секції.

## Організація полів в адмінці

- Перед кожною логічною групою полів додавати `Message` із назвою групи та шириною `100%`, щоб наступні поля починалися з нового рядка.
- `Message` пояснює належність полів в адмінці; заголовок, який має відображатися на сайті, зберігати в окремому контентному полі.
- Пов'язані поля розміщувати поруч, добираючи ширину за обсягом даних і зручністю: рівні колонки для порівнянних полів, вужчі для коротких підписів, ширші для описів і повторювачів.
- Не прив'язувати пропорції жорстко до назв конкретних полів. Перевірити читабельність і зручність вкладених повторювачів.
- Для списку з заголовком створити окреме поле заголовка та окремий Repeater зі значеннями.
- Не додавати редактору технічні поля CSS-класів, службових селекторів чи параметрів реалізації.

## Наповнення сторінок та багатомовність

- Перед створенням сторінки перевіряти вже наявні сторінки та їхні переклади. Використовувати відповідні існуючі записи без дублів.
- Призначити шаблон `Constructor` сторінкам, секції яких інтегруються, і заповнити їхній `constructor` контентом із верстки у вихідному порядку.
- Завантажити потрібні зображення й фони у медіабібліотеку, перевіривши, чи вони вже імпортовані, і заповнити ними поля. Створення порожніх полів без перенесення наявного контенту не завершує інтеграцію.
- Для посилань спочатку визначити їхній тип за URL. Для реального посилання на сторінку знайти або створити її, а потім заповнити поле посилання. Для `#anchor` сторінку не створювати.
- Перевірити зареєстровані мови Polylang. Для кожної відповідної мовної сторінки призначити шаблон, заповнити та перекласти контент конструктора, зв'язати сторінки як переклади.
- Внутрішні посилання й зв'язки із записами повинні відповідати мові сторінки. Перевірити доступну інтеграцію ACF та Polylang, не припускати автоматичного перекладу значень.
- Дані конструктора зберігати на самій сторінці. `ACF Options For Polylang` стосується глобальних опцій і не замінює мовне наповнення сторінок.
- Повторний запуск не має створювати дублікати сторінок, медіа, типів записів, таксономій, груп полів або рядків конструктора та перезаписувати відредагований користувачем контент.

## Погоджені рішення для www-svitvody

- Створити через інтерфейс реєстрації ACF власний тип запису `Товари` та пов'язану ієрархічну таксономію `Категорії товарів`, спочатку перевіривши наявні сутності та конфлікти ключів. Їхні визначення мають бути доступні для редагування в ACF.
- Товари потрібні для зберігання даних і вибору в погоджених блоках; окремих публічних сторінок товарів і категорій не потрібно.
- Для типу запису встановити `public = false`, `publicly_queryable = false`, `show_ui = true`, `show_in_menu = true`, `show_in_nav_menus = false`, `exclude_from_search = true`, `has_archive = false`, `rewrite = false`, `query_var = false`.
- Для таксономії встановити `hierarchical = true`, `public = false`, `publicly_queryable = false`, `show_ui = true`, `show_in_nav_menus = false`, `rewrite = false`, `query_var = false`; прив'язати її до типу товарів.
- Зіставити ці параметри з налаштуваннями встановленої версії ACF і перевірити фактичну реєстрацію WordPress. Самого вимкнення rewrite недостатньо для заборони прямого відкриття записів.
- Товари й категорії повинні редагуватися в адмінці та вибиратися через погоджені ACF-поля. У шаблонах не генерувати посилання на їхні single-сторінки або архіви. Перевірити відсутність публічного відкриття як через красиві URL, так і через query-параметри; виключити ці сутності з публічних sitemap.
- Якщо товари потребують мовних версій, перевірити підтримку непублічного типу та таксономії в установленому Polylang і узгодити поля, які перекладаються; мовні зв'язки не мають вмикати публічні URL.
- Інформаційний блок `Як ми працюємо` - контент із Repeater, без окремого типу запису.
- Блок `Акції` з вручну заданими цінами - Repeater із контентними полями, без автоматичного зв'язку з товарами.
- Блок `Пропозиції` - Repeater із контентом і посиланнями на відповідні сторінки; спочатку використати існуючі сторінки.
- Блок `Вартість води` прив'язати до товару води через `Post Object`. Цінові картки - це рівні одного товару за кількістю бутлів, а не окремі товари. Repeater із мінімальною кількістю, ціною за бутель, заголовком, позначкою, підписом одиниці та текстом кнопки зберігати в товарі. Валюта спільна для його рівнів. Зберегти якір секції для навігації.
- Інші інформаційні списки також реалізувати через Repeater. Наявність типу `Товари` сама по собі не змінює ці погоджені рішення.
- У типі `Товари` розрізняти воду з ціновими рівнями та додаткові товари/послуги через поле вибору. У всіх блоках `Додаткові товари та послуги` автоматично виводити опубліковані додаткові товари поточною мовою, без товару води. Початкові позиції `Застава за бутель` і `Помпа ECONOM PLUS` залишаються додатковими товарами. Не дублювати картки окремо на кожній сторінці.
- У таксономії товарів використовувати дві логічні категорії з мовними версіями Polylang: `Аксесуари` для всіх додаткових товарів і послуг, включно із заставним бутлем, та `Вода` для основного товару води. Не створювати окрему категорію тари. Кожен товар має належати рівно до однієї з цих категорій відповідно до його типу.
- Назву, підпис, ціну, валюту, зображення, alt і текст кнопки брати з товару. Створити та зв'язати його мовні версії через Polylang. Дані супутніх товарів у кошику мають використовувати те саме джерело; нові опубліковані товари повинні з'являтися без змін PHP або JavaScript.
- Кнопки додавання товарів мають однакову поведінку незалежно від перекладу їхнього тексту. Не додавати до ACF тексти інтерфейсу кошика чи форми попапу.
- У записі товару забезпечити редагування всіх контентних даних його картки, а також окремого опису товару в мінікошику. Це дані товару, а не глобальні тексти інтерфейсу кошика. Додавання з карток і зі списку супутніх товарів має змінювати один кошик: синхронно оновлювати позиції, кількість, лічильник і суму та зберігати їх під час переходів між сторінками.
- Конкретні блоки, що читатимуть дані з типу `Товари`, і набір полів товару узгодити на початку реалізації, якщо вони ще не визначені користувачем.

## Вода, кошик і заявки

- Товар питної води та заставна тара - різні позиції. Натискання цінової картки води передає в кошик ID цього товару та початкову кількість відповідного рівня, без створення окремого товару на кожен тариф.
- При зміні кількості брати ціну рівня з найбільшою мінімальною кількістю, яка не перевищує замовлену. Не дозволяти замовлення нижче найменшого рівня. Усі числові ціни та пороги брати з товару, без незалежних копій у JavaScript або сторінках.
- Каталог та тарифи мають бути доступні кошику на всіх сторінках, навіть без блоку вартості. Мовні версії товару зв'язати через Polylang; зберігати стабільний ключ кошика при зміні мови.
- Заявку з форми й поточним складом мінікошика зберігати в окремому непублічному типі запису `Заявки`. Зберігати ім'я, телефон, адресу, дату доставки, повідомлення, мову, товари, кількість, застосований ціновий рівень, ціну за одиницю та загальну суму. Поле часу доставки не використовувати у формі, перевірці заявки чи сповіщеннях.
- Контакти й склад заявки доступні тільки уповноваженому адміністратору. Не відкривати заявки через публічні URL, REST API, пошук чи sitemap. Передбачити стан обробки заявки в адмінці.
- Сервер перевіряє поля, товари, кількості й сам перераховує суму за актуальними даними товарів. Не довіряти назвам і цінам із браузера. Якщо показана клієнту сума застаріла, вимагати її перевірки, а не зберігати непомітно змінену суму.
- Зберігати в заявці незмінний знімок цін і назв на час оформлення. Подальше редагування товару не повинно змінювати попередні заявки.
- Додати перевірку запиту, обмеження частоти спроб і захист від дублювання при повторному або одночасному надсиланні. Показувати успіх та очищати форму/кошик тільки після підтвердженого збереження. При помилці зберігати введені дані для повторної спроби.
- Після підтвердженого збереження показувати у попапі окремий виразний стан успіху з номером заявки та повідомленням про подальший зв'язок. Автоматично закривати попап через 8 секунд, дозволяючи користувачу закрити його раніше; перед наступним відкриттям повністю відновлювати форму.
- Перевірити граничні кількості тарифів, зміну ціни з адмінки, додавання супутніх товарів, збереження заявки та її приватність, повторні запити й помилки мережі. Тестові заявки видалити після перевірок.

### Сповіщення про заявки

- У Telegram додавати URL-кнопку `Перейти до замовлення` на захищену сторінку заявки в адмінці замість текстового URL. Формувати адресу з поточного WordPress; локальна адреса доступна лише на комп'ютері із сайтом. Суми передавати звичайним текстом без HTML-сутностей, наприклад `1 100,00 грн`.

- У глобальних налаштуваннях створити окрему вкладку `Сповіщення заявок`: перемикач поштових сповіщень, Email одержувача, перемикач Telegram, токен бота, Chat ID групи та необов'язковий ID теми.
- Налаштування технічні, спільні для всіх мов, доступні лише адміністратору. Структура полів видима в ACF. Токен не показувати на сайті або повторно в полі адмінки; порожнє значення зберігає наявний токен, окрема опція дозволяє видалити його.
- Пошту надсилати через `wp_mail()`. SMTP налаштовує користувач окремим плагіном; не додавати власні SMTP-поля або перехоплення `phpmailer_init` у тему.
- Сповіщення надсилати тільки після збереження заявки, фоново через WP-Cron. Помилка доставки не скасовує заявку й не показує клієнту фальшиве повідомлення про помилку оформлення.
- У заявці показувати стан кожного каналу та давати адміністратору можливість повторити ненадіслані сповіщення. Успішно надісланий канал не повторювати. Для неоднозначної мережевої помилки спочатку перевірити канал: автоматичний повтор може створити дубль.
- Telegram інтегрувати через [sendMessage](https://core.telegram.org/bots/api#sendmessage), без довільного HTML з форми, з обмеженням довжини та посиланням на повну заявку в захищеній адмінці. Не записувати токени або сирі HTTP-помилки з секретним URL у статуси чи журнали теми.
- Поштове тестове надсилання не запускати: користувач налаштує поштовий плагін пізніше. Telegram дозволено тестувати після окремого дозволу користувача та заповнення ключів у налаштуваннях; для тестових заявок вимикати Email без зміни глобальних налаштувань. Не вважати збереження ключів підтвердженням реальної доставки.

## Перевірка результату

- Статичні тексти інтерфейсу, повідомлення перевірки та інші рядки, записані безпосередньо в PHP або JavaScript, оформлювати через стандартний text domain теми WordPress і підтримувати у `.pot`, `.po` та `.mo`. Для JavaScript передавати перекладені WordPress рядки у структурованому об'єкті до виконання основного скрипту.
- Не дублювати у файлах перекладу контент і підписи, які редактор заповнює через ACF, меню WordPress, сторінки, записи або глобальні мовні опції. Такі значення перекладати у відповідній мовній сутності чи опції Polylang.

- Перевірити синтаксис змінених PHP-файлів у Docker та відповідність імен layouts, файлів і полів.
- В адмінці перевірити доступність шаблону `Constructor`, прихований звичайний редактор, видимість групи ACF і можливість редагувати структуру layouts та значення.
- Перевірити додавання, переставлення, повторення та вимкнення секцій, збереження полів, порожні значення й повторювачі. Тимчасові перевірочні зміни повернути після перевірки.
- Візуально звірити сторінки з версткою у браузері на desktop і mobile для зареєстрованих мов: тексти, фони, зображення, кнопки, якорі та інтерактивні елементи.
- Перевірити відсутність дубльованих DOM ID, помилок JavaScript та зламаних зображень; переконатися, що перенесені секції відображаються один раз.
- Перевірити, що зміна контенту в адмінці відображається у відповідній секції та мовній сторінці, а товари й категорії залишаються доступними для редагування без публічних сторінок.
