# Частина 2. Робота з header.php

## Призначення

- `header.php` відповідає за початок HTML-документа і верхню повторювану частину сайту.

## Що має бути в header.php

- `<!doctype html>`.
- Відкриття тега `html` з WordPress-функцією `language_attributes()`.
- Тег `head` з базовими meta-тегами.
- Виклик `wp_head();` перед закриттям `head`.
- Відкриття тега `body` з WordPress-функцією `body_class()`.
- Виклик `wp_body_open();` одразу після відкриття `body`, якщо він доречний у темі.
- Повторюваний HTML-блок header з верстки: логотип, навігація, контакти, кнопки, перемикач мови та інші верхні елементи.

## WordPress-адаптація

- Статичні посилання на assets у `header.php` замінювати на `get_template_directory_uri()`.
- Посилання на головну сторінку замінювати на `home_url('/')`.
- HTML-структуру не ламати: теги, відкриті в `header.php`, мають коректно продовжуватися в `index.php` або закриватися там, де це логічно.
- `wp_head();` має залишатися у `head`, а не переноситися нижче в тіло сторінки.

## Меню WordPress

- Усі меню, які є у header-верстці, потрібно виводити через стандартний функціонал меню WordPress.
- Для desktop-меню створювати окрему menu location і виводити її через `wp_nav_menu()`.
- Якщо у верстці є мобільне меню, для нього створювати окрему menu location і окреме меню в адмінці WordPress.
- Не залишати пункти меню жорстко прописаними в `header.php`, якщо вони мають редагуватися через WordPress.
- Перед створенням меню потрібно проаналізувати всі посилання у верстці header і визначити, що є сторінкою, а що є якорем на блок.
- Перед створенням сторінки для пункту меню потрібно перевірити, чи така сторінка вже існує в WordPress.
- Якщо потрібна сторінка вже створена, не створювати дубль, а використати наявну сторінку і прикріпити її до пункту меню.
- Під час рішення, створювати сторінку чи ні, первинним є URL з верстки, а не тільки текст пункту меню.
- Якщо у верстці URL пункту є якорем, наприклад `#pricing`, не створювати окрему сторінку для цього пункту навіть тоді, коли текст пункту виглядає як назва сторінки.
- Якщо посилання у верстці веде на окрему сторінку, спочатку потрібно створити або використати відповідну сторінку WordPress.
- Після створення сторінок потрібно створити меню в базі даних WordPress і додати пункти меню як посилання на відповідні сторінки, а не як довільні custom URL.
- Якщо пункт меню веде на якір на цій же сторінці, його потрібно залишати як якір або посилання на сторінку з якорем відповідно до структури сайту і не створювати для нього окрему сторінку.
- Не створювати сторінку тільки через наявність `#anchor`, якщо це внутрішній якір до секції поточної сторінки.
- Порядок роботи має бути таким: аналіз посилань з верстки, створення потрібних сторінок, створення меню, прикріплення сторінок до пунктів меню, окреме додавання якірних пунктів там, де вони справді є якорями.
- Якщо встановлений плагін багатомовності, перед створенням сторінок і меню потрібно перевірити, які мови зареєстровані у плагіні.
- Перед створенням перекладу сторінки потрібно перевірити, чи перекладена сторінка вже існує для відповідної мови.
- Якщо перекладена сторінка вже існує, не створювати дубль, а використати її і за потреби зв'язати з основною сторінкою як переклад.
- Для кожної зареєстрованої мови потрібно створити відповідні сторінки цією мовою.
- Перекладені сторінки потрібно зв'язати між собою як переклади однієї сторінки у multilingual-плагіні.
- Заголовки сторінок для іншої мови потрібно перекласти відповідною мовою, а не дублювати український текст.
- Відносно кількості зареєстрованих мов потрібно створити окремі дублікати кожного меню для кожної мови.
- Меню кожної мови має містити пункти, прикріплені до сторінок цієї ж мови, а не до сторінок іншої мови.
- Меню різних мов потрібно зв'язати між собою як переклади одного меню, якщо це підтримує multilingual-плагін.
- Якщо використовується Polylang, кожне мовне меню потрібно прикріпити до відповідної мовної локації меню, наприклад `Header desktop menu Українська` і `Header desktop menu Русский`, а не тільки створити меню і зв'язати його як переклад.
- Для Polylang потрібно перевірити, що у його налаштуваннях `nav_menus` для активної теми кожна базова location має menu ID для кожної мови.
- Меню для кожної мови потрібно створювати або прив'язувати відповідно до логіки multilingual-плагіна, щоб перемикач мови і пункти меню працювали коректно.

## Налаштування header в адмінці

- Для інформації header, яка не є меню, потрібно створити глобальну сторінку налаштувань через ACF Pro.
- На сторінці налаштувань має бути tab `Header`.
- До tab `Header` додавати поля для логотипу, контактів, телефонів, кнопок, текстів кнопок, посилань, месенджерів, перемикача мови та інших подібних елементів.
- Якщо для логотипу створюється ACF-поле, потрібно завантажити відповідний логотип у медіабібліотеку WordPress і записати його в це поле в адмінці.
- Не залишати поле логотипу порожнім, якщо у верстці вже є відповідний файл логотипу.
- Якщо сайт багатомовний, потрібно перевірити, чи підтримує поточна версія Polylang мовні значення для ACF options page.
- Якщо встановлений плагін `ACF Options For Polylang`, глобальні ACF options потрібно заповнювати окремо для кожної мови через мовний перемикач в адмінці.
- Для `ACF Options For Polylang` потрібно враховувати, що значення можуть зберігатися з мовним суфіксом locale, наприклад `options_ru_RU_*`, а не тільки в базових `options_*`.
- Контент header у глобальних ACF options потрібно перекладати для кожної мови: тексти кнопок, заголовки контактів, заголовки телефонів, графік роботи та інші текстові значення.
- Спільні для мов елементи, наприклад той самий логотип, теж потрібно заповнити у мовних options, якщо поле не підтягується автоматично як fallback.
- Не створювати для клієнта технічні ACF-поля на кшталт `CSS-клас іконки`, класів верстки, службових селекторів або інших технічних параметрів дизайну.
- Якщо у повторюваному списку з верстки кожен елемент має свою іконку через іконковий шрифт, наприклад Font Awesome, потрібно створити зрозуміле ACF-поле `Іконка` типу `Select` з людськими назвами варіантів.
- Значення select для шрифтових іконок має бути внутрішнім ключем, наприклад `telegram`, `viber`, `facebook`, `instagram`, а відповідний CSS-клас іконки потрібно визначати в коді теми.
- Якщо у повторюваному списку іконка у верстці є файлом, SVG або `<img>`, потрібно створити ACF-поле `Іконка` типу `Image` або `File` і виводити її через `<img>`.
- Не змішувати принципи: шрифтові іконки керуються через `Select`, файлові іконки через `Image` або `File`.
- Іконки, CSS-класи та інші технічні деталі відображення залишати в коді теми, якщо вони не є контентною частиною повторюваного елемента.
- Якщо елемент складається з кількох частин, поля потрібно розділити або згрупувати логічно.
- Перед кожною логічною групою ACF-полів потрібно додавати поле типу `Message` як заголовок групи в адмінці.
- Таке `Message`-поле має мати ширину `100%`, щоб візуально розмежувати групу і перенести наступні поля на новий рядок.
- Заголовок `Message` має пояснювати, до якого блоку належать наступні поля, наприклад контакти, графік роботи, попап заявки, форма заявки, кнопки або інший логічний блок з верстки.
- Якщо кілька ACF-полів належать до одного логічного блоку у верстці, їх потрібно розташовувати поруч у адмінці через налаштування ширини поля, щоб редактор бачив зв'язок між ними.
- Для парних пов'язаних полів, наприклад зображення і його alt-текст, можна використовувати пропорцію ширини `50%` на `50%`, якщо це зручно для заповнення.
- Для груп з трьох пов'язаних полів можна використовувати приблизно рівні колонки або іншу пропорцію, яка відповідає обсягу контенту.
- Якщо частина полів має короткий зміст, наприклад короткий текст кнопки, короткий заголовок блоку або перемикач, таким полям можна задавати меншу ширину в адмінці, наприклад `15%`, `20%`, `25%` або `33%`, а ширші поля залишати для довшого контенту.
- Ширину ACF-полів потрібно підбирати не жорстко за назвою поля, а за логікою блоку, довжиною очікуваного контенту і зручністю редагування в адмінці.
- Якщо у верстці є список однотипних опцій, наприклад телефони, месенджери, соціальні мережі або пункти контактів, можна використовувати тип поля ACF `Repeater`.
- Для блоків на кшталт `Наші телефони` потрібно створювати окреме ACF-поле для заголовка блоку і окреме поле або `Repeater` для самих телефонів.
- Для блоків на кшталт `Графік роботи` потрібно створювати окреме ACF-поле для заголовка блоку і окремі поля або `Repeater` для рядків графіка роботи.
- Якщо у dropdown або подібному вкладеному блоці є кілька груп інформації, кожну групу потрібно структурувати окремо: заголовок групи, список значень, посилання, іконки та додатковий текст.
- Наприклад, кнопка `Контакти`, яка відкриває або показує додатковий контент, має мати окрему групу полів для тексту кнопки, телефонів, графіка роботи, посилань та інших внутрішніх контентних елементів.
- Кнопка `Замовити` або подібні CTA-кнопки мають мати окремі поля для тексту, посилання або modal target, і за потреби додаткових атрибутів.
- Якщо прихований попап заявки має окремі контентні налаштування для header, для нього потрібно створити окремий ACF tab одного рівня з `Header` і `Footer`, наприклад `Попап заявки`.
- Tab `Попап заявки` не має бути блоком або message-групою всередині tab `Header`; це має бути самостійна вкладка на сторінці глобальних налаштувань.
- У tab `Header` мають залишатися поля, які керують саме елементами header, наприклад текст кнопки замовлення або мобільної кнопки.
- У tab попапу заявки переносити тільки ті поля, які користувач явно погодив для редагування в адмінці, наприклад modal ID, контактний вступний текст, телефони попапу та месенджери.
- Усередині tab попапу заявки потрібно додавати `Message`-заголовки для логічних груп, наприклад `Налаштування попапу`, `Контакти попапу`.
- Якщо у попапі заявки є месенджери з іконками через іконковий шрифт, використовувати `Repeater` з полями `Іконка` типу `Select`, `Назва` і `URL`.
- Якщо у попапі заявки месенджери або інші іконки є файлами, SVG або `<img>`, замість `Select` потрібно використовувати поле `Image` або `File`.
- Якщо у попапі, формі заявки або іншому прихованому блоці виводиться телефон, потрібно перевірити, чи це може бути список телефонів; якщо так, використовувати `Repeater`, а не одиночне поле або жорстко прописаний один телефон.
- Якщо телефонний список уже створений для header, його можна повторно використати у попапі або формі заявки, щоб не дублювати однакові поля.
- У `header.php` потрібно виводити ці значення з налаштувань, а не залишати їх жорстко прописаними, якщо вони мають редагуватися в адмінці.

## Багатомовність і перемикач мови

- Якщо у верстці спостерігається багатомовність сторінок або є перемикач мови, його потрібно інтегрувати у WordPress.
- Перед інтеграцією перевірити, чи встановлені та активні плагіни для багатомовності у Docker-оточенні WordPress.
- Перемикач мови має працювати за тим принципом, який закладений у проєкті або у встановленому multilingual-плагіні.
- Якщо multilingual-плагін не використовується, не залишати перемикач повністю фіктивним без пояснення; потрібно або підключити його до реальної логіки, або узгодити подальший принцип реалізації.
- Візуальний вигляд перемикача мови має відповідати верстці.

## ACF і плагіни

- Перед створенням полів або сторінок налаштувань потрібно перевірити, які плагіни встановлені та активні у Docker-оточенні WordPress.
- Особливо перевіряти, чи доступний ACF Pro, бо в цьому проєкті він може бути встановлений через локальні plugins.
- Якщо ACF Pro доступний, поля для header потрібно створювати так, щоб їх можна було редагувати в адмінці WordPress.
- Поля ACF мають бути керовані з адмінки, а не тільки описані через код без можливості редагування користувачем.
- Групи полів ACF мають бути видимі в ACF -> Групи полів, якщо користувач має надалі редагувати структуру полів через адмінку.
- Якщо потрібно створити ACF option page або field groups, робити це з урахуванням того, щоб користувач міг редагувати значення через адмінку.
- Не ховати важливі значення header тільки в PHP-коді, якщо вони мають бути контентом або налаштуваннями сайту.

## Перевірка

- Після змін у `header.php` потрібно перевіряти себе не тільки синтаксично, а й візуально у браузері.
- Візуально перевіряти desktop і mobile стани header, меню, мобільне меню, dropdown-блоки, кнопки, логотип, контакти, перемикач мови та відступи.
- Якщо проєкт працює через Docker, відкривати локальний сайт у браузері через Docker URL проєкту і перевіряти, що header виглядає як у верстці.
